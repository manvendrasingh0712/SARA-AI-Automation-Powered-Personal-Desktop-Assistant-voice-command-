# SARA AI Complete Practical Audit Report

## 1. Executive Summary
The SARA AI project is a highly capable and robust local-first desktop assistant with an impressive modular architecture following the recent refactor. The backend successfully manages audio processing (VAD, STT, TTS) and LLM fallback routing without catastrophic crashes on startup. 

However, during practical end-to-end execution, several edge cases and race conditions were identified. The most critical issues involve threading crashes when the application shuts down (background threads attempting to communicate with a destroyed GUI) and API integration failures (Gemini rate limits and embedding 500 errors) that degrade long-term memory. Additionally, two test suites have fallen out of sync with the codebase.

Overall Health: **Good, but requires stabilization on background threads and API requests.**

---

## 2. Fully Working
The following components were verified practically and confirmed to function correctly:
* **Application Startup**: `main.py` bootstraps the environment safely, successfully loads CUDA DLLs if present, and spins up background daemon threads (`reminders`, `notifications`, `proactive`).
* **Health Check & Diagnostics**: `run_startup_diagnostics` accurately probes for `config.py`, Gemini API keys, Kokoro model files, and audio devices without blocking.
* **LLM Fallback Mechanism**: When Gemini hits a 429 rate limit, the system gracefully cascades to the local Ollama instance (`qwen3:4b-instruct-2507-q4_K_M`), keeping the conversation alive.
* **Audio Subsystem**: `faster_whisper` properly detects speech and identifies languages, while Kokoro ONNX successfully loads the model weights.
* **Proactive Engine**: Spawns properly on startup and continually tracks state for scheduled triggers.

## 3. Problems Found

**Problem:**
GUI crashes on application shutdown or window close.

**Reproduction:**
Run `main.py`, allow background threads (e.g. notifications, proactive engine) to start, then close the PyWebView window.

**Expected:**
The application shuts down cleanly, joining or terminating background threads before they can access the UI.

**Actual:**
A severe error is logged: `System.ComponentModel.InvalidAsynchronousStateException: An error occurred invoking the method. The destination thread no longer exists.`

**Evidence:**
Observed continuously in `logs/sara.log`:
```
ERROR    | pywebview | Error occurred in script
Traceback (most recent call last):
System.ComponentModel.InvalidAsynchronousStateException: An error occurred invoking the method.  
The destination thread no longer exists.
```

**Root Cause:**
Background loops (e.g. `_writer_loop` in RAG or the proactive daemon) attempt to call `ui_update()` to send a toast notification after the main PyWebView context has already been destroyed by the user closing the window.

**Best Solution:**
Implement a thread-safe `_window_closed` flag in `sara.gui.app.core.py` and wrap all `ui_update` invocations to ignore async dispatches if the flag is set. Join threads strictly on exit.

**Severity:**
Critical

---

**Problem:**
Long-term memory/RAG embedding generation fails silently on the backend.

**Reproduction:**
Speak or send a command that triggers memory extraction/consolidation while using Gemini as the embedding backend.

**Expected:**
The application successfully contacts the Gemini API to retrieve embeddings and stores them in the SQLite DB.

**Actual:**
The request fails, skipping memory consolidation.

**Evidence:**
Observed repeatedly in `logs/sara.log`:
```
INFO | httpx | HTTP Request: POST https://generativelanguage.googleapis.com/v1beta/models/gemini-embedding-001:batchEmbedContents "HTTP/1.1 500 Internal Server Error"
```

**Root Cause:**
The `gemini-embedding-001` model string used in `sara/core/llm/clients.py` and `config.py` is either deprecated or incompatible with the specific payload generated by `google-genai==1.23.0`, causing Google's servers to return a 500. 

**Best Solution:**
Update `Config.EMBEDDING_MODEL` to `"text-embedding-004"` (the current standard for Gemini embeddings) and implement exponential backoff on 500 responses in `_get_embedding_vector`.

**Severity:**
High

---

**Problem:**
Gemini backend hits Rate Limits (429) causing unnecessary fallback to Ollama.

**Reproduction:**
Send rapid queries or let the proactive engine/memory consolidation trigger multiple background LLM requests concurrently.

**Expected:**
The application batches or delays requests to stay within free-tier Gemini API limits.

**Actual:**
The Google API returns 429 Too Many Requests, forcing a fallback to the slower local Ollama model.

**Evidence:**
```
INFO | httpx | HTTP Request: POST https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:streamGenerateContent?alt=sse "HTTP/1.1 429 Too Many Requests"
```

**Root Cause:**
Lack of a robust retry/backoff wrapper around `client.models.generate_content` and `client.models.embed_content`.

**Best Solution:**
Wrap LLM and embedding calls in `sara/core/llm/clients.py` with `tenacity.retry` using an exponential backoff strategy for HTTP 429 responses.

**Severity:**
Medium

---

**Problem:**
Automated testing fails due to undocumented PyWebView API surface changes.

**Reproduction:**
Run `.venv\Scripts\pytest tests\test_api_surface.py`

**Expected:**
The test confirms no unexpected API methods are exposed to the frontend.

**Actual:**
The test fails, complaining about 3 undocumented methods.

**Evidence:**
```
AssertionError: ['get_ui_prefs', 'set_ui_pref', 'sync_notes_now'] is not false : Api class exposes 3 new method(s) not in this test's expected list
```

**Root Cause:**
The `EXPECTED_METHODS` whitelist in `tests/test_api_surface.py` was not updated when `sara/gui/app/ui_prefs.py` and `sara/gui/app/settings.py` were introduced.

**Best Solution:**
Update `EXPECTED_METHODS` in `tests/test_api_surface.py` to include `"get_ui_prefs"`, `"set_ui_pref"`, and `"sync_notes_now"`.

**Severity:**
Low

---

**Problem:**
Context History logic pollutes test expectations with time-dependent mood hints.

**Reproduction:**
Run `.venv\Scripts\pytest tests\test_sara_context_history.py`

**Expected:**
The test validates that the exact string `application: notepad` is passed to the context.

**Actual:**
The test fails sporadically depending on the time of day it is run.

**Evidence:**
```
AssertionError: "application: notepad (It's morning — a bit more upbeat/energetic tone fits.)" != 'application: notepad'
```

**Root Cause:**
`_route_chat_message` in `sara/orchestrator/dispatcher.py` dynamically appends a time-of-day tone (e.g., morning vs late night) to the `reference_context` string, but the test suite does not mock the system clock.

**Best Solution:**
Use `unittest.mock.patch` to freeze `datetime.datetime.now` during the test, and update the assertion to expect the deterministic tone hint.

**Severity:**
Low

---

**Problem:**
Invalid display name parsing spam from screen_brightness_control.

**Reproduction:**
Launch the app on a machine with a generic or unbranded PnP monitor.

**Expected:**
The brightness tool initializes silently.

**Actual:**
Spams the logs with parsing errors.

**Evidence:**
```
WARNING  | screen_brightness_control.windows | exception parsing edid str for DISPLAY\CMN1521\5&1da3265f&0&UID4354_0 - EDIDParseError: parsed EDID returned invalid display name
```

**Root Cause:**
The `screen_brightness_control` package attempts to parse EDID metadata from the OS, which is malformed on some monitors, causing the library's internal parser to log warnings.

**Best Solution:**
Suppress warnings from the `screen_brightness_control` logger in `logging_config.py` by setting its log level to `ERROR`.

**Severity:**
Low

## 4. Root-Cause Summary
- **Asynchronous GUI Teardown:** The primary stability issue is background threads lacking awareness of the main UI thread's lifecycle, leading to `InvalidAsynchronousStateException`.
- **API Versioning/Model Rot:** The embedding model name `gemini-embedding-001` is causing hard 500 errors, likely because it is incompatible with the updated `google-genai` client payload.
- **Testing Desync:** Recent features were implemented (UI preferences, time-based tone prompts) without corresponding updates to the automated tests.

## 5. Recommended Fix Order
1. **Critical:** Implement a thread-safe window closed flag in the GUI core to stop the pywebview asynchronous thread crash.
2. **High:** Update `Config.EMBEDDING_MODEL` to `text-embedding-004` to restore Long-Term Memory functionality.
3. **Medium:** Add backoff/retry logic for Gemini API 429 rate limits.
4. **Low:** Fix `test_api_surface.py` and `test_sara_context_history.py` tests.
5. **Low:** Suppress the EDID parsing warnings in `logging_config.py`.

## 6. Untested Items
* **Visual Verification of GUI Elements:** Cannot be tested. The test environment is a headless Windows runner with no visual desktop shell (session 0 isolation). pywebview successfully binds the backend, but visual transitions, hover effects, CSS themes, and animations cannot be observed or clicked.
* **Audio Voice Input/Output Verification:** Cannot be tested. The environment lacks a physical microphone and speaker. While the `health_check.py` confirmed `sounddevice` can detect virtual audio devices, real-world waking via microphone and actual playback could not be functionally audited.
* **Settings Persistence (Visual):** Could not click through the UI to verify that theme updates visually persist upon reload, though the backend `PreferencesDB` method calls behave as expected programmatically.
